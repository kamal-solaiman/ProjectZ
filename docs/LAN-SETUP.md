# تشغيل البرنامج على أكثر من جهاز على نفس الشبكة المحلية (LAN)

التطبيق يعمل بمعمارية **عميل ← LAN ← SQL Server** على الجهاز الرئيسي. لا يوجد وسيط ولا خدمة مركزية إضافية: كل جهاز يشغّل نسخة كاملة من `FitohPhone.exe`، وكل نسخة تتصل مباشرة بقاعدة `FitohPhone` على الخادم. لذلك لا تُشارك أي حالة بين الأجهزة، ولا يحتاج العميل إلى تثبيت SQL Server.

| العنصر | مكانه | ملاحظات |
|---|---|---|
| SQL Server 2016 SP1 Express | الجهاز الرئيسي فقط | عنوان ثابت أو DHCP reservation |
| `FitohPhone.exe` + `connectionsettings.json` | كل جهاز | نفس مجلد النشر يُنسخ كما هو |
| `dbo.Users` | قاعدة `FitohPhone` | جدول واحد، قراءة فقط من التطبيق |
| الجلسة بعد الدخول | ذاكرة كل جهاز | لا تُحفظ ولا تُشارك |

الحد الأدنى للتحقق: جهازان على نفس الشبكة يسجّلان الدخول في نفس الوقت بنفس الحساب ونفس القاعدة. خطوات الإثبات في نهاية هذا الملف.

---

## 1. تجهيز الجهاز الرئيسي (مرة واحدة)

نفّذ أولًا [تجهيز الجهاز الرئيسي](SERVER.md) بالكامل (إنشاء القاعدة وتشغيل `sql/01` و`sql/02`)، ثم أكمل ما يلي لأن العملاء لن يتصلوا بدونه:

1. **تفعيل TCP/IP**: SQL Server Configuration Manager → SQL Server Network Configuration → Protocols → **TCP/IP = Enabled**.
2. **منفذ ثابت**: TCP/IP Properties → IP Addresses → **IPAll** → أفرغ `TCP Dynamic Ports` واضبط `TCP Port = 1433`. أعد تشغيل خدمة الـ instance. المنفذ الثابت يغني عن SQL Server Browser وعن UDP 1434.
3. **عنوان ثابت للخادم**: IP ثابت أو DHCP reservation. سجّل العنوان، وسيُستخدم حرفيًا في إعدادات كل جهاز: `192.168.1.10,1433`.
4. **جدار الحماية** (على الخادم، بصلاحيات Administrator):

   ```powershell
   New-NetFirewallRule -DisplayName "FitohPhone SQL LAN" -Direction Inbound `
     -Protocol TCP -LocalPort 1433 -Action Allow -Profile Private `
     -RemoteAddress 192.168.1.0/24
   ```

   القيود الثلاثة مهمة: **TCP 1433 فقط**، **ملف Private/LAN فقط**، و**نطاق الشبكة الداخلية فقط**. لا تفتح المنفذ للإنترنت ولا تستخدم `Any` في `RemoteAddress`.
5. **هوية اتصال العملاء** (أقل صلاحية ممكنة): SQL Login مخصص `FitohPhoneClient` مربوط بـ user في `FitohPhone` مع `SELECT` على `dbo.Users` فقط.
   - إن كان لديكم Active Directory فالأفضل Windows Authentication عبر مجموعة `DOMAIN\FitohPhoneUsers` بدل كلمة مرور في ملف.
   - لا تستخدم `sa` ولا `db_owner`، ولا تضع حساب المسؤول في الملف.
6. **Mixed Mode** مطلوب فقط عند استخدام SQL Login: Server Properties → Security → **SQL Server and Windows Authentication mode** ثم أعد تشغيل الخدمة.
7. **قواعد Express**: تسمح بعدد اتصالات كبير (لا يوجد حد للعملاء في Express)، لكن حدودها هي ذاكرة 1 GB، ومعالج واحد بحد أقصى 4 أنوية أو 24 GB، وقاعدة بحد 10 GB. تسجيل الدخول هنا خفيف جدًا (SELECT صف واحد)، فلا مشكلة مع عشرات الأجهزة.
8. **التحقق من الشبكة** من أي جهاز عميل:

   ```powershell
   ping 192.168.1.10
   Test-NetConnection 192.168.1.10 -Port 1433     # TcpTestSucceeded = True
   ```

   نجاح TCP لا يثبت صلاحيات SQL ولا TLS؛ إثبات ذلك يكون بتسجيل دخول فعلي من كل جهاز.

## 2. نشر نفس المجلد على كل جهاز

1. من جهاز تطوير Windows: `dotnet publish` كما في [README](../README.md) → `publish/win-x64`.
2. انسخ **محتويات** المجلد إلى مسار محلي على كل جهاز، مثل `C:\Apps\FitohPhone`. لا تشغّل من قرص شبكة أو مشاركة، ولا تنسخ مجلد المصدر بدل مخرجات publish.
3. الجميع يستخدم **نفس ملف `connectionsettings.json`** بجوار الـ EXE. لا تحتاج نسخة مختلفة لكل جهاز، والمجلد نفسه يعمل على الرئيسي وعلى العملاء.
4. لا يحتاج العميل إلى .NET Runtime ولا SQL Server (نشر Self-Contained). يحتاج فقط Windows x64 مدعوم ووصول LAN للخادم.

## 3. ملف الإعدادات: قسم مشترك + استثناءات اختيارية

```json
{
  "Default": {
    "Server": "192.168.1.10,1433",
    "Database": "FitohPhone",
    "IntegratedSecurity": false,
    "UserId": "FitohPhoneClient",
    "Password": "REPLACE_LOCALLY_WITH_REAL_SECRET",
    "Encrypt": true,
    "TrustServerCertificate": true,
    "ConnectTimeoutSeconds": 15
  },
  "Machines": {
    "MAIN-PC": {
      "Server": "192.168.1.10,1433",
      "Database": "FitohPhone",
      "IntegratedSecurity": true,
      "UserId": "",
      "Password": "",
      "Encrypt": true,
      "TrustServerCertificate": true,
      "ConnectTimeoutSeconds": 15
    }
  }
}
```

### كيف يختار البرنامج القسم؟

1. يقرأ **اسم جهاز Windows** الحالي (`COMPUTERNAME`، يظهر بالأمر `hostname`).
2. إن وُجد قسم في `Machines` بهذا الاسم (دون حساسية لحالة الأحرف) وله `Server` صالح → يُستخدم.
3. وإلا يُستخدم قسم `Default`. هذا هو الحال المعتاد: **كل الأجهزة تستخدم `Default` بلا أي تعديل**.
4. إن لم يوجد أي قسم صالح → رسالة إعداد واضحة على شاشة الدخول تذكر اسم الجهاز والأقسام الموجودة.

`Machines` اختياري تمامًا. استخدمه فقط إذا احتاج جهاز معيّن شيئًا مختلفًا، مثل:

- خادم احتياطي أو نسخة اختبار لقسم معين: `"LAPTOP-TEST": { "Server": "192.168.1.11,1433", ... }`
- الجهاز الرئيسي يستخدم Windows Authentication بينما العملاء SQL Login.
- جهاز في شبكة فرعية أخرى يحتاج `ConnectTimeoutSeconds` أكبر.

ملاحظات على القيم:

- `Server` صيغته `IP,Port` بفاصلة (ليست نقطتين): `192.168.1.10,1433`. مقبول أيضًا اسم الجهاز أو اسم instance مثل `MAIN-PC\\SQLEXPRESS` (شرطتان عكسيتان في JSON).
- في المصدر الحالي `192.168.1.46` هو العنوان الافتراضي المؤقت؛ **استبدله بالعنوان الفعلي للخادم** على كل الأجهزة. `SERVER_NAME` يبقى مرفوضًا.
- كل الأجهزة يجب أن تحمل `Database` = `FitohPhone` لتقرأ نفس الجدول؛ اختلافها يعني قاعدتين مختلفتين.
- `Encrypt=true` مع `TrustServerCertificate=true` هو الإعداد الصحيح لـ Express ذي الشهادة الذاتية. عند تثبيت شهادة CA داخلية: ثبّت سلسلة الثقة على **كل** عميل ثم اضبط `TrustServerCertificate=false`.
- لا تستخدم `.` أو `(local)` أو LocalDB في إعدادات العملاء، فهي تشير إلى الجهاز نفسه لا إلى الخادم.

الملف نصي وليس خزنة أسرار. قيّد NTFS ACL على مجلد `C:\Apps\FitohPhone` لمستخدم التطبيق والمسؤول فقط، ولا تضع نسخة تحتوي السر الحقيقي في Git أو في مرفقات. Windows Authentication يلغي الحاجة لحفظ السر أصلًا.

## 4. ماذا يحدث على كل جهاز؟

- كل جهاز يفتح اتصالًا مستقلًا بقاعدة `FitohPhone` عند كل محاولة دخول، ويغلقه بعدها (يُعاد استخدامه من pool داخل نفس العملية فقط).
- التحقق يجري داخل جهاز العميل: يُجلب hash الحساب ثم يُفحص محليًا بـ PBKDF2؛ كلمة المرور لا تُرسل إلى SQL ولا تُحفظ.
- بعد نجاح الدخول تصبح الجلسة **محلية في الذاكرة**: لا صفوف جلسات في القاعدة، ولا تزامن بين الأجهزة. دخول جهاز أو خروجه أو إغلاقه لا يؤثر على بقية الأجهزة.
- لا يكتب التطبيق شيئًا في القاعدة أثناء الدخول أو الخروج، فلا تعارض كتابة بين الأجهزة.
- الحساب `admin` ليس جلسة واحدة: يمكن تسجيل الدخول به من عدة أجهزة في نفس الوقت. لا يوجد قفل حساب على مستوى القاعدة.
- قطع الشبكة بعد نجاح الدخول لا يغلق نافذة البرنامج؛ يظهر أثر الانقطاع عند **محاولة دخول جديدة**.

## 5. إثبات أن الأجهزة متصلة فعليًا

على الخادم، وبصلاحيات مسؤول SQL (تحتاج `VIEW SERVER STATE`، **ولا تُمنح للتطبيق**)، شغّل أثناء وجود الأجهزة في شاشة الدخول أو بعد دخولها مباشرة:

```sql
SELECT s.host_name, s.program_name, s.login_name,
       DB_NAME(s.database_id) AS DatabaseName, c.client_net_address
FROM sys.dm_exec_sessions AS s
JOIN sys.dm_exec_connections AS c ON c.session_id = s.session_id
WHERE s.program_name = N'FitohPhone';
```

- `program_name` = `FitohPhone` بفضل `ApplicationName` في connection string، وهو ما يميّز جلسات التطبيق عن جلسات SSMS.
- `host_name` و`client_net_address` هما دليل الجهازين المختلفين.
- `client_net_address` هو عنوان العميل كما يراه الخادم، و`host_name` هو اسم الجهاز المرسل في الاتصال.
- الاتصالات قد تبقى pooled, فإن لم تظهر الجلسات أعد المحاولة بعد إغلاق البرنامج على الأجهزة.

التحقق الكامل على الأجهزة نفسها:

| # | الخطأ الشائع | الدليل المطلوب |
|---|---|---|
| 1 | تسجيل الدخول من الجهاز الرئيسي | نافذة رئيسية، واسم الحساب ظاهر |
| 2 | تسجيل الدخول من جهاز عميل في نفس الوقت | نجاح، وبقاء نافذة الرئيسي مفتوحة |
| 3 | استعلام `sys.dm_exec_sessions` | صفّان+ بـ `program_name = FitohPhone` و`host_name` مختلف |
| 4 | تسجيل خروج على العميل ثم دخول مرة أخرى | لا تأثير على الرئيسي، ولا نوافذ يتيمة |
| 5 | إيقاف جهاز العميل (Shutdown) | الرئيسي يعمل طبيعيًا؛ القاعدة سليمة |
| 6 | محاولة دخول بعد إيقاف خدمة SQL | رسالة اتصال واضحة على كل الأجهزة، واستعادة بعد تشغيلها |

سجّل نتائجك في [سجل القبول](ACCEPTANCE.md) (الاختباران 6 و7 موسّعان لهذا الغرض).

## 6. استكشاف الأعطال على الشبكة

الرسائل تظهر على شاشة الدخول. السطر الصغير أسفل الشاشة يعرض الجهاز والقسم والخادم والقاعدة ونوع المصادقة المستخدمة فعليًا، فابدأ منه.

| الأثر | السبب الغالب | الحل |
|---|---|---|
| «لا يوجد قسم اتصال صالح لهذا الجهاز» | قسم `Default` ناقص أو `Server` فارغ | أضف `Default` بعنوان صالح، أو قسمًا باسم الجهاز |
| خطأ 26 | اسم instance خاطئ أو Browser متوقف | استخدم `IP,1433` بمنفذ صريح |
| خطأ 40 / 53 / 11001 | اسم الخادم لا يُحلّ | استخدم IP مباشرة |
| خطأ 10061 / انتهاء مهلة | الخدمة متوقفة أو TCP/IP معطّل أو الجدار مغلق | راجع خطوة 1 على الخادم |
| خطأ 4060 | القاعدة غير موجودة أو لا صلاحية عليها | نفّذ `sql/01` وامنح user على `FitohPhone` |
| خطأ 18456 | فشل حساب الاتصال | راجع `UserId`/`Password` أو login الخاص بـ Windows |
| خطأ 18452 | نوع المصادقة غير مفعّل | فعّل Mixed Mode أو استخدم Windows Authentication |
| خطأ 229 | لا صلاحية SELECT | `GRANT SELECT ON OBJECT::dbo.Users TO [FitohPhoneClient]` |
| رسالة شهادة TLS | شهادة غير موثوقة | `TrustServerCertificate=true` للشبكة الداخلية، أو ثبّت CA على كل عميل |
| رسالة SSPI | Windows Authentication خارج Domain | استخدم SQL Login واضبط `IntegratedSecurity=false` |
| يعمل على جهاز ويفشل على آخر | فرق في الملف أو Firewall خاص بالعميل أو شبكة مختلفة | قارن `Default` على الجهازين، ثم `Test-NetConnection` |

## 7. الحدود الأمنية (مهمة)

الاتصال المباشر يعني أن **كل جهاز عميل يستطيع قراءة جدول `dbo.Users` بما فيه الهاشات**، ويستطيع مالك الجهاز تعديل نسخة العميل محليًا. تسجيل الدخول هنا ليس حاجز صلاحيات ضد مالك جهاز خبيث، بل تحقق من هوية مستخدم التطبيق. لذلك:

- اقتصر على شبكة داخلية موثوقة، ولا تعرّض 1433 للإنترنت.
- امنح أقل صلاحية (`SELECT` على جدول واحد) ولا تمنح `VIEW SERVER STATE` للتطبيق.
- قيّد ملفات العميل بـ ACL، واستخدم Windows Authentication إن أمكن.
- خذ نسخًا احتياطية دورية للقاعدة، وراقب من يدخل الشبكة.
