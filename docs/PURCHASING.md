# إصلاح حفظ فاتورة الشراء

## السبب المؤكد

رسالة «تعذر حفظ فاتورة الشراء في قاعدة البيانات» كانت تخفي خطأ SQL Server التالي:

```text
SQL 137: Must declare the scalar variable "@Invoice".
```

أمر `ReceiveUnits` الذي يسجّل كل قطعة في `dbo.InventoryUnits` كان يقرأ الفاتورة بالشرط:

```sql
FROM dbo.PurchaseInvoices i WHERE i.Id = @Invoice;
```

لكن الكود لم يكن يضيف `@Invoice` إلى `SqlCommand.Parameters`. يرفض SQL Server الأمر قبل إدراج القطعة، وتُلغى معاملة الفاتورة بالكامل؛ لذلك لا تُحفظ فاتورة ناقصة ولا يتغير المخزون أو الرصيد.

أصلح الفحص الآلي كشف أربعة معاملات أخرى غير مربوطة في مسارات المشتريات، وكانت ستظهر بعد تجاوز الخطأ الأول:

| الموضع | المعامل الناقص سابقًا | القيمة الممررة الآن |
| --- | --- | --- |
| `ReceiveUnits` — إدراج وحدة المخزون | `@Invoice` | معرّف فاتورة الشراء |
| `ReceiveUnits` — حركة `Supply` | `@Actor` | معرّف المستخدم المنفذ |
| `UpdateInvoice` — تعديل بند قائم | `@Id` | معرّف البند المحفوظ |
| `InsertLedger` — الحركة المالية | `@Balance` | الرصيد بعد الحركة، بنوع `DECIMAL(19,2)` |
| `AddActivity` — سجل نشاط الفاتورة | `@Actor` | معرّف المستخدم المنفذ |

## ما تغيّر في الكود

- ربط المعاملات الخمسة بقيمها وأنواعها صراحةً.
- إصلاح `tools/static_checks.py` ليفحص أوامر SQL متعددة الأسطر داخل نصوص C# الحرفية `@"..."`؛ الفحص السابق كان يتجاوزها ويسمح بمرور الخطأ.
- إظهار رقم ونص خطأ SQL غير المصنّف بدل إخفائه خلف رسالة عامة، مع رسالة خاصة للمعامل غير المربوط (137/8178).
- ضبط خيارات `SET` المطلوبة للفهارس المفلترة عند كل اتصال بالمشتريات، حتى لو أعاد التجميع استخدام جلسة سابقة بخيارات غير متوافقة.

**هذا إصلاح برمجي ولا يحتاج تعديل جداول أو حذف بيانات أو تشغيل سكربت ترحيل.** يبقى `sql/12_EnablePurchasing.sql` مطلوبًا إذا كان الخطأ مستقلًا متعلقًا بالصلاحيات (229/230).

## التحقق الآلي

اختبار `tests/ProjectZ.Purchase.Sql.Tests` يشغّل `PurchaseRepository` الحقيقي، وليس نسخة محاكية، على SQL Server LocalDB معزول ينشئه `Run.ps1` ثم يحذفه. يستخدم حساب SQL مؤقتًا بصلاحيات السكربتات نفسها، ولا يقرأ إعدادات خادم المحل ولا يتصل بها.

يغطي الاختبار:

- حفظ فاتورة ببند عادي وبند متتبع بالسيريال، مع كمية أكبر من واحد.
- الدفع الجزئي والمقسّم، الآجل الكامل، السداد الكامل، وسداد لاحق.
- تطابق الرأس والبنود والوحدات وروابطها وحركات المخزون والمدفوعات والدفتر المالي والأنشطة والتدقيق والأرصدة.
- تعديل بند قائم وزيادة كميته وتسوية فرق الدفع.
- إعادة قراءة الفواتير والملاحظات العربية من SQL.
- إصلاح خيارات الجلسة غير المتوافقة على اتصال معاد استخدامه.
- فشل متعمد في آخر كتابة: التراجع عن كل الصفوف والترقيم والأرصدة.
- نقص صلاحية الإدراج: رسالة قابلة للتنفيذ وتراجع كامل، ثم نجاح الحفظ بعد استعادة الصلاحية.

أعاد الاختبار إنتاج الخطأ 137 قبل الإصلاح، ثم نجح بعد الإصلاح مع بناء WPF ونشر artifact في Windows CI:

- [تشغيل ناجح على GitHub Actions](https://github.com/kamal-solaiman/ProjectZ/actions/runs/43592328907)
- أمر التشغيل المحلي على Windows مع LocalDB:

```powershell
pwsh tests/ProjectZ.Purchase.Sql.Tests/Run.ps1
```

الاختبار الآلي استخدم LocalDB 15 بمستوى توافق 130. لا يغني عن القبول اليدوي النهائي على SQL Server 2016 SP1+ وأجهزة LAN الفعلية.

## النشر على أجهزة المحل

1. خذ نسخة احتياطية وأغلق ProjectZ على الأجهزة التي ستُحدّث.
2. نزّل artifact `ProjectZ-win-x64` من تشغيل CI الناجح، أو ابنِ النشر بأمر `dotnet publish` الموضح في README.
3. انسخ ملفات النشر الجديدة، مع الاحتفاظ بملف `connectionsettings.json` المضبوط لكل عميل.
4. افتح «شراء فاتورة» واحفظ فاتورة اختبارية بمورد وصنفين ودفعة جزئية، وتأكد من ظهورها في «فواتير المشتريات» وزيادة المخزون ونقص الرصيد بقدر الدفعة.

لا تعد محاولة حفظ فاتورة فشل حفظها سابقًا قبل تحديث النسخة؛ بعد التحديث يمكن إدخالها من جديد لأن المعاملة الفاشلة لم تترك صفوفًا جزئية.
