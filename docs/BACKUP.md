# شاشة النسخ الاحتياطي والاسترجاع

> **إذا عرض 24 الخطأ `50248` أو 25 الخطأ `50250` برسالة فصل حساب النسخ، ثم ظهرت رسائل أعمدة أو أنواع مفقودة:** [خطوات التشخيص والاستكمال](#علاج-50248-و50250). لا تحذف شرط الصلاحيات ولا تنشئ الأعمدة يدويًا.

## الغرض

شاشة مستقلة ضمن فئة **الإعدادات → النسخ الاحتياطي** تنفّذ عمليتين إداريتين على SQL Server:

1. **BACKUP DATABASE** إلى ملف `.bak` كامل لقاعدة البيانات المضبوطة في `connectionsettings.json` (`ProjectZ` افتراضيًا).
2. **RESTORE DATABASE** من ملف `.bak` موجود، مع استبدال قاعدة البيانات نفسها ببيانات الملف. لا يُكتب اسم القاعدة ثابتًا في الكود؛ يُقرأ من إعداد `Database` ويمرّ بأمان كمعرّف SQL مقتبس.

الشاشة لا تحفظ إعدادات المحل ولا تغيّر المظهر؛ شاشة **اعدادات عامة** مسؤولة عن هوية المحل، وشاشة **المظهر** مستقلة. لكل شاشة مضيف Grid منفصل في `MainWindow.xaml`، واختيار إحداهما لا يعرض الأخرى فوقها.

## مسار الملف: تنبيه أساسي

أوامر `BACKUP` و`RESTORE` تُنفَّذ على **جهاز SQL Server**، والمسار يُقرأ هناك، وليس على جهاز العميل:

- إذا كان SQL Server على نفس الجهاز، فمسار مثل `C:\ProjectZ\Backups\ProjectZ_20261114_1200.bak` يعمل.
- إذا كان SQL Server على جهاز آخر، استخدم مسارًا موجودًا على الخادم أو مشاركة UNC يصل إليها **حساب خدمة SQL Server**، مثل `\\SERVER\Backups\ProjectZ_20261114_1200.bak`.
- زر **استعراض** يختار مجلدًا/ملفًا من جهاز العميل فقط؛ لذلك لا يُعتمد عليه لاكتشاف مسار الخادم. يمكن كتابة المسار مباشرة.
- لا تتحقق الشاشة من وجود المجلد أو الملف محليًا قبل الإرسال؛ SQL Server يعيد الخطأ 3201/3202 إذا تعذّر الوصول إلى المسار، وتعرضه الشاشة برسالة عربية.

## كيف تعمل الشاشة

- **معلومات القاعدة**: تُقرأ من `sys.database_files` (الحجم) و`msdb.dbo.backupset` (آخر نسخة). `backup_start_date` يُعرض بتوقيت جهاز SQL Server كما هو، دون تحويل خاطئ من UTC.
- **اسم الملف**: يبدأ بـ`ProjectZ_yyyyMMdd_HHmmss.bak` ويُعاد توليده تلقائيًا بعد كل نسخة ناجحة، إضافة إلى زر **اسم جديد**، حتى لا تستبدل النسخة التالية ملفًا سابقًا بسبب تكرار الاسم. من يكتب اسمًا موجودًا بنفسه فسيستبدل الملف عمدًا لأن الأمر يستخدم `WITH INIT, FORMAT, CHECKSUM`.
- **الاسترجاع**: يتم من اتصال منفصل إلى `master`، ثم `ALTER DATABASE [<اسم القاعدة من الإعدادات>] SET SINGLE_USER WITH ROLLBACK IMMEDIATE`، ثم `RESTORE ... WITH REPLACE, RECOVERY`. في `finally` تُعاد القاعدة إلى `MULTI_USER` من نفس اتصال `master` حتى لو فشل الاسترجاع. الاتصال بالقاعدة المستهدفة أثناء الاستعادة كان يبقيها مشغولة ويمنع العملية.
- **بعد الاسترجاع**: تُعاد قراءة معلومات القاعدة وتُفرّغ خانة المسار. يجب تحديث بقية الشاشات أو إعادة تشغيل البرنامج؛ الجلسات الأخرى كانت قد قُطعت أثناء `SINGLE_USER`. إذا كان اسم القاعدة في `connectionsettings.json` غير `ProjectZ`، فالاسترجاع يستهدف الاسم المضبوط نفسه.
- **قائمة الملفات**: تُقرأ محليًا من جهاز العميل للعرض فقط. إذا كان مجلد الخادم غير متاح من الجهاز، ستكون القائمة فارغة، وهذا لا يعني أن النسخ غير موجودة؛ استخدم المسار الكامل في بطاقة الاسترجاع.
- **قفل النموذج**: أثناء النسخ أو الاسترجاع تُعطَّل الحقول والأزرار (`IsBusy`/`IsIdle`) لمنع عمليتين متداخلتين.

## الصلاحيات المطلوبة على SQL Server

لا تمنح `ProjectZClient` حقوق النسخ والاسترجاع لحل خطأ في الشاشة. **تستخدم الشاشة اتصال البرنامج نفسه**؛ حساب «مدير» داخل التطبيق لا يبدّل هوية SQL. على أجهزة الكاشير المحدودة يُتوقع رفض الاسترجاع، وليس هناك حقل سري ثانٍ لإدخال اتصال إداري. نفّذ عمليات النسخ والاسترجاع من SSMS أو من مهمة إدارية منفصلة على الخادم، ولا تغيّر `connectionsettings.json` في أي نقطة بيع إلى حساب النسخ.

إذا كان لديك بالفعل مسؤول نسخ مستقل يعمل، **تخطَّ `18`**. للتفويض الاختياري للنسخ **والاسترجاع معًا**: ينشئ مسؤول SQL تسجيل الدخول `ProjectZBackupAdmin` خارج البرنامج بسرّ محلي، ويربط به مستخدمًا مطابقًا في `ProjectZ` (`CREATE USER [ProjectZBackupAdmin] FOR LOGIN [ProjectZBackupAdmin];` إذا لم يوجد). بعد التحقق من الربط، ينفذ المسؤول [النسخة الحالية من 18_EnableBackupRestore.sql](../sql/18_EnableBackupRestore.sql). تستهدف **هذه الهوية فقط**، ولا تنشئ كلمة مرور ولا تسحب عضوية قديمة من الكاشير. `db_owner` داخل `ProjectZ` و`dbcreator` على مستوى **الخادم كله** صلاحيتان واسعتان للاسترجاع؛ لا حاجة لهما لتثبيت 24 أو 25، ولا تستخدم هذا التفويض لمهمة تحتاج النسخ فقط.

## علاج 50248 و50250

1. **أوقف نقاط البيع ولا تفتحها بين السكربتين.** الرفض هنا يخص **صلاحيات `ProjectZClient`**، وليس نقص صلاحيات منفذ الترقية؛ تشغيل الملف القديم بحساب أقوى لا يحلّه. كانت نسخة `18` القديمة تمنح الكاشير `db_owner` و`dbcreator`. وعند رفض أول دفعة من 24 أو 25، كان SSMS العادي يواصل بعد `GO`: لم يُنشأ `RefundOfPaymentId` أو نوع `PurchaseItemSelection` أو جداول الإشعارات، وقد تكون بعض الإجراءات والمنح اللاحقة نُفّذت. لا تعتبر «Completion time» دليل نجاح، ولا تعالج كل رسالة على حدة.
2. **افحص من اتصال SQL إداري مستقل.** افتح [SeparateLegacyBackupRoles.sql](../sql/admin/SeparateLegacyBackupRoles.sql) كاملًا في نافذة جديدة. اترك `@Apply = 0` (الافتراضي): يعرض اسم الخادم والقاعدة وحساب المسؤول، تطابق مستخدم الكاشير مع تسجيل الدخول، مالك القاعدة، والأدوار الفعلية والمباشرة التي يفحصها 24 و25، **دون تغيير**. راجع هوية الاتصال الفعلية على كل جهاز أيضًا؛ لا يقرأ SQL ملفات إعدادات العملاء.
3. **قبل سحب أي دور:** خذ نسخة بالهوية الإدارية المنفصلة واختبر استعادتها على **مثيل SQL معزول**؛ السكربتات تستهدف قاعدة اسمها `ProjectZ` و`dbcreator` دور على مستوى المثيل، فلا تختبر تبديل أدوار الخادم على مثيل المحل. تأكّد أن مهام النسخ والاسترجاع لم تعد تستخدم الكاشير. إذا كان `LoginMatchesUser=1` والمانع هو عضوية `db_owner` أو `dbcreator` **المباشرة** فقط، غيّر `@Apply` محليًا إلى `1` ونفّذ الملف كاملًا. لا يحذف حسابًا أو بيانات أو أذونات التشغيل. إذا ظهر `sysadmin` أو كانت القاعدة مملوكة للكاشير أو بقيت عضوية موروثة أو كان الربط غير مطابق، **توقف**: على المسؤول مراجعة مصدر الحق والملكية، لا إزالة أدوار أخرى بالتخمين. راجع أيضًا أي منح إدارية مخصصة؛ فهذه ليست مراجعة لكل صلاحيات المثيل.
4. أعد الفحص بـ`@Apply = 0` في **اتصال جديد**. المطلوب `LoginMatchesUser=1` و`IsSysadmin=IsDbOwner=IsDbCreator=0`، ومالك `ProjectZ` ليس الكاشير. تحقّق من [المتطلبات السابقة](SERVER.md): المخطط 06 وحساب التشغيل، إصدار 07 الحالي و09 و13–16 للصيانة؛ وللمشتريات 07 و12 و22 الحالي بعد 09 و11. **لا تُعد تشغيل 04 لتصفير كلمة المرور، ولا 18 القديم.** تسجيلات الدخول وأدوار الخادم لا تنتقل مع ملف `.bak`؛ على المثيل المعزول يجهّز المسؤول ربط المستخدم بتسجيل الدخول الصحيح قبل تجربة الترقية.
5. على النسخة المعزولة أولًا، افتح **النسخة المحدّثة الكاملة** من [24](../sql/24_EnableMaintenanceSettlement.sql) في SSMS بحساب إداري، ثم [25](../sql/25_EnablePurchaseSettlement.sql) **فقط بعد نجاح 24**. كل ملف معاملة مستقلة، تشمل البنية والإجراءات والأذونات؛ عند الفشل يتراجع ذلك الملف إلى ما قبل المحاولة، حتى في SSMS العادي. هذا لا يتراجع عن تشغيل سابق بالملف القديم: تُستكمل الكائنات الناقصة وتُحدَّث الإجراءات المعروفة عند الإعادة الناجحة. لا تحذف جدولًا أو نوعًا أو إجراءً لإعادة المحاولة. استخدم `sqlcmd -b` إذا كنت تشغّل مجموعة ملفات، وتوقف عند أول خطأ. لا تستأنف التشغيل بعميل قديم.

**تحقق بعد نجاح الملفين** في `ProjectZ` كمسؤول. القيم التالية يجب ألّا تكون `NULL`؛ هذه علامات تثبيت، وليست إثباتًا لمطابقة الأرصدة:

```sql
USE [ProjectZ];
SELECT COL_LENGTH(N'dbo.MaintenancePayments',N'RefundOfPaymentId') AS RefundLinkBytes,
       OBJECT_ID(N'dbo.WriteMaintenanceMoney',N'P') AS WriteMoney,
       OBJECT_ID(N'dbo.ReopenMaintenanceTicket',N'P') AS ReopenTicket,
       TYPE_ID(N'dbo.PurchaseItemSelection') AS ItemType,
       TYPE_ID(N'dbo.PurchaseReturnSelection') AS ReturnType,
       OBJECT_ID(N'dbo.vwSupplierCreditBalances',N'V') AS CreditView,
       (SELECT column_id FROM sys.columns WHERE object_id=OBJECT_ID(N'dbo.vwPurchaseInvoiceSummary',N'V') AND name=N'NeedsReview') AS ReviewColumn,
       OBJECT_ID(N'dbo.ReturnPurchaseDocument',N'P') AS ReturnPurchase;
```

من اتصال كاشير جديد، دون تنفيذ أي عملية مالية، تحقّق من الهوية ومن عينة للأذونات. المتوقع `1، 1، 0، 0` للأذونات بالترتيب؛ إن كانت الهوية غير متوقعة أو لم تتطابق النتيجة فلا تفتح نقاط البيع:

```sql
USE [ProjectZ];
SELECT ORIGINAL_LOGIN() AS TillLogin, USER_NAME() AS TillUser,
       HAS_PERMS_BY_NAME(N'dbo.SettleMaintenanceTicket','OBJECT','EXECUTE') AS CanSettle,
       HAS_PERMS_BY_NAME(N'dbo.PayPurchaseDocument','OBJECT','EXECUTE') AS CanPay,
       HAS_PERMS_BY_NAME(N'dbo.MaintenancePayments','OBJECT','UPDATE') AS CanRewritePayment,
       HAS_PERMS_BY_NAME(N'dbo.PurchaseInvoices','OBJECT','UPDATE') AS CanRewriteInvoice;
```

أكمل [اختبار القبول من جهازين](ACCEPTANCE.md) على النسخة المعزولة. عند النقل إلى خادم المحل خذ نسخة حديثة، وأعد فحص الأدوار والمتطلبات هناك قبل تطبيق الملفين مع توقف الأجهزة ونشر العميل المطابق. إذا استُخدمت الأجهزة بعد الفشل القديم، احتفظ بالنسخة والسجلات وطابق مستندات تلك الفترة قبل استئناف العمل؛ لا تُستنتج أرصدة تاريخية من نجاح التثبيت.

## استخدام الشاشة في بيئة إدارية معزولة فقط

1. لا تستخدم هذه الشاشة على جهاز كاشير لإجراء الاسترجاع. في بيئة إدارية معزولة، تحقّق من اتصال SQL المستهدف قبل البدء؛ شارة «متصل بقاعدة البيانات» وحدها لا تثبت الصلاحيات.
2. من **الإعدادات → النسخ الاحتياطي**.
3. **نسخة**: اكتب مسار المجلد على جهاز SQL Server، وراجع اسم `.bak` أو اضغط **اسم جديد**، ثم **أخذ النسخة الاحتياطية**.
4. **استرجاع**: اكتب مسار `.bak` على جهاز SQL Server أو اختره من استعراض الجهاز المحلي إن كان الخادم هو نفس الجهاز، ثم اضغط زر الاسترجاع وأكّد التحذير.
5. راقب شريط الحالة للنتيجة؛ يبقى ظاهرًا أسفل الشاشة خارج منطقة التمرير.

## ملاحظات القبول

- تحقق من إنشاء ملف `.bak` فعليًا على الخادم، ومن ظهوره في قائمة الملفات إذا كان المجلد متاحًا للعميل.
- أعد تشغيل التطبيق بعد تغيير اسم المحل أو استرجاع قاعدة، وتأكد من عمل الدخول.
- الاسترجاع عملية مدمّرة: اختبرها على قاعدة تجريبية أولًا.
- لم يُشغّل WPF أو SQL Server داخل بيئة الفحص النصي؛ يلزم Windows مع SQL Server 2016 SP1 أو أحدث.
